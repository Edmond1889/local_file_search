나중에 손님이 “고양이”나 “프로젝트 일정”이라고 말하면 비슷한 내용을 찾아준다.

## 2. app.py — 가게 문을 열고 직원을 배치한다

`build_service()`는 ImageEncoder, DocumentEncoder, KoreanTextEncoder, DocumentEmbedder, Repository, DocumentLoader를 준비한다.
그 객체들을 DocumentSearch에 전달하고, 연결이 끝난 서비스 객체를 반환한다.

여기서 **클래스는 직원의 업무 설계도, 객체는 그 설계도로 실제 준비한 직원**이라고 생각하면 된다.

```python
image_encoder = ImageEncoder(model_name=model_name, pretrained=pretrained)
document_encoder = DocumentEncoder(image_encoder=image_encoder)
```

첫 줄은 이미지 인코더 객체를 만든다. 두 번째 줄은 그 객체를 문서 이미지 담당자에게 전달한다.
DocumentEncoder가 다른 이미지 모델을 하나 더 만드는 것이 아니라 이미 만든 ImageEncoder를 공유한다.
KoreanTextEncoder도 이제 같은 ImageEncoder의 모델 객체를 전달받는다. 사진 담당자와 문장 담당자가 같은 장비를 함께 쓰는 셈이다.
문장을 토큰 번호로 바꾸는 tokenizer도 함께 전달한다. 같은 OpenCLIP 모델을 두 번 읽지 않는다.

`model_name`은 사용할 모델 구조의 이름이고 `pretrained`는 학습된 가중치의 이름이다.
가중치는 모델이 학습하면서 얻은 숫자들이다. 내 파일을 읽는 순간 모델을 새로 학습시키는 것은 아니다.

`TemporaryDirectory`는 이번 작업에 쓸 임시 장부 보관 장소다.
서비스에 `session_directory`를 보관하는 이유는 분석·검색 도중 임시 폴더가 먼저 정리되지 않도록 하기 위해서다.

실행 명령에 `--gui`가 있으면 Tkinter 창을 열고, 없으면 터미널에서 입력받는 `main()`을 실행한다.

## 3. 스캐너와 로더 — 봉투를 찾는 일과 여는 일

같은 파일 안에 있지만 두 일은 다르다.

**DocumentScanner.scan_files()는 봉투의 위치를 찾는다.**
폴더와 하위 폴더를 돌아다니며 지원하는 확장자의 파일 경로를 하나씩 돌려준다.
`yield`는 경로를 발견할 때마다 다음 코드에 하나씩 넘겨주는 문법이다.
이때는 PDF 글이나 이미지 픽셀을 읽지 않는다.

**DocumentLoader.process_file(path)는 그 봉투를 연다.**
확장자를 보고 `load_pdf()`, `load_pptx()`, `load_image()` 중 하나를 호출한다.
그래서 연결 코드에서 확장자를 또 구분할 필요가 없다.

| 입력 | 로더가 실제로 꺼내는 것 |
|---|---|
| JPG·JPEG·PNG·WEBP | PIL 이미지 하나 |
| PDF | 추출 가능한 페이지 본문 |
| PPTX | 슬라이드의 글·표 텍스트와 추출한 이미지 |

`PIL 이미지`는 파일 경로가 아니라 메모리에 읽어온 픽셀 데이터다.
PDF에서 글을 꺼내는 것과 PDF 페이지를 사진처럼 만드는 것은 다르다. 현재 PDF 로더는 본문만 추출한다.
PPTX는 슬라이드 전체 화면을 사진으로 만들지 않으며, 한 슬라이드에 이미지가 여러 개면 마지막으로 읽은 이미지 하나가 남는다.

## 4. DocumentChunk — 봉투에서 꺼낸 내용 카드

파일 하나가 PDF 10페이지일 수도 있으므로 로더가 읽은 내용을 작은 단위로 묶어 전달한다.
그 묶음이 `DocumentChunk`다. 현재 PDF는 본문이 있는 페이지별, PPTX는 내용이 있는 슬라이드별로 만든다.
긴 문장을 일정 길이로 다시 잘게 자르는 기능은 없다.

| 필드 | 카드에 적힌 뜻 |
|---|---|
| file_name / file_path | 어느 파일에서 나온 내용인지 |
| page_number | 몇 번째 페이지·슬라이드인지. 단독 이미지는 1 |
| text | 꺼낸 본문. 이미지 파일이면 빈 문자열 |
| chunk_type | pdf, pptx, image 중 어떤 종류인지 |
| image | 읽은 PIL 이미지. 그림이 없으면 None |

`None`은 “이 카드에는 이미지 값이 없다”라는 뜻이다.
슬라이드에 글과 그림이 함께 있으면 카드 하나에 `text`와 `image`가 함께 들어갈 수 있다.
이 경우 글과 그림을 각각 맞는 인코더로 전달한다.

## 5. 인코더 세 종류 — 어느 직원에게 내용을 맡기는가?

### ImageEncoder — 사진을 읽는 직원

PIL 이미지를 받아 OpenCLIP의 512차원 벡터로 만든다.
512차원이라는 말은 사진 한 장을 숫자 512개로 표현한다는 뜻이다.
모델 입력에 맞게 크기와 색상 등을 준비하는 작업도 이 코드가 맡는다.

### DocumentEncoder — 문서 속 그림을 사진 직원에게 넘기는 창구

이름 때문에 PDF나 PPTX 파일 자체를 읽는 것으로 오해하기 쉽다.
현재 이 클래스가 받는 것은 로더가 꺼낸 **PIL 이미지**다.

```python
return self.image_encoder.encode(image)
```

현재 핵심 동작은 이 전달이다. 독립적인 문서 본문 모델이 아니다.
`encode_batch()`도 여러 이미지를 같은 이미지 인코더에 전달한다.
현재 로더가 PDF 페이지를 이미지로 만들지 않으므로 이 연결에서 PDF 페이지 이미지가 자동 생성되지는 않는다.

### DocumentEmbedder — 글을 읽고 비교까지 하는 직원

`embed_chunks(chunks)`는 청크에서 본문만 모아 ko-SRoBERTa로 인코딩한다.
본문 청크 목록은 `self.chunks`, 숫자 배열은 `self.embeddings`에 보관한다.
`search(query)`는 검색 문장도 같은 모델로 바꾸고 본문 벡터와 비교한다.
최신 생성자는 `DocumentEmbedder(model=...)`로 외부 모델을 전달받을 수도 있다. 현재 앱은 본문용 ko-SRoBERTa를 따로 준비한다.
빈 본문은 인코딩 목록에서 제외한다. 연결 코드도 본문이 있는 청크만 넘겨 청크와 벡터의 순서를 맞춘다.

이 팀원 코드는 **인코딩과 유사도 검색을 함께 포함**한다.
그래서 현재 파일이 similarity 폴더에 있어도 인코딩 기능이 사라지는 것은 아니다.

## 6. 검색 문장은 왜 두 가지 방식으로 바꾸나?

가게 안에 서로 다른 기준으로 만든 지도 두 장이 있다고 생각하면 된다.
지도 A의 좌표를 지도 B에 그대로 찍으면 엉뚱한 장소가 된다.

| 검색 대상 | 파일을 숫자로 만드는 모델 | 검색 문장을 숫자로 만드는 모델 |
|---|---|---|
| 문서 본문 | DocumentEmbedder의 ko-SRoBERTa | 같은 DocumentEmbedder의 ko-SRoBERTa |
| 이미지 | ImageEncoder의 OpenCLIP | KoreanTextEncoder의 같은 OpenCLIP 모델·가중치 |

파일과 문장을 같은 기준으로 바꿔야 비교가 의미를 가진다.
본문 검색 점수와 이미지 검색 점수는 기준이 다르므로 합치지 않는다.
검색 문장을 받는다고 모두 KoreanTextEncoder로 보내는 것도 아니다.

## 7. DocumentInfo와 DB — 내용 카드와 접수 장부는 다르다

DocumentChunk가 파일에서 꺼낸 내용 카드라면 **DocumentInfo는 파일 자체의 접수 카드**다.

| 담는 것 | DocumentChunk | DocumentInfo |
|---|---|---|
| 파일 경로·이름 | 포함 | 포함 |
| 페이지·본문·이미지 | 포함 | 미포함 |
| 확장자·크기·해시·시각·DB 번호 | 별도 접수 정보로 관리하지 않음 | 포함 |

`@dataclass`는 이런 정보 묶음을 쉽게 만들도록 생성자 등을 준비해주는 Python 기능이다.
AI 모델을 정의하거나 실행하는 문법이 아니다.

연결 코드는 `DocumentInfo(file_path=..., file_name=..., ...)` 형태로 값을 채운다.
`이름=값`은 키워드 인자다. 접수 카드의 어느 칸에 적는지 이름으로 지정하는 방식이다.
DB는 `document.file_name`처럼 값을 꺼내 `document_metadata` 테이블에 저장한다.
`file_hash`는 파일 내용으로 계산한 SHA-256 문자열이며, 검색용 의미 벡터와 다르다.
`created_at`은 이 정보가 만들어진 시각, `updated_at`은 실제 파일의 마지막 수정 시각이다.

`Repository.save(info)`가 반환하는 `file_id`는 장부의 접수 번호다.
검색으로 번호를 찾으면 `find_by_id(file_id)`로 파일 이름과 경로를 다시 읽는다.
현재 DB는 파일 정보만 저장하고 본문·이미지 벡터는 프로그램 메모리에 보관한다.

### 예전에 있던 루트 document_info.py는 왜 없어졌나?

예전에는 팀원 DB가 옛 import 이름을 써서 안내 표지판이 필요했다.
최신 DB는 `from .db_info import DocumentInfo`로 같은 폴더의 자료형을 직접 가져온다.
이제 표지판을 거치지 않아 루트 document_info.py는 제거했다. 실제 접수 카드 양식인 `database/db_info.py`는 그대로 필요하다.
이번 db_info 변경은 주석 삭제뿐이며 접수 카드의 필드는 바뀌지 않았다.

## 8. connection/service.py — 내가 맡은 연결 업무

진행 담당자는 사진이나 글을 이해하는 AI를 직접 만들지 않는다.
로더와 인코더에 일을 맡기고, 결과가 어느 파일에서 나왔는지 연결한다.

### analyze(folder_path): 검색하기 전에 접수를 끝낸다

```text
폴더 확인 → 스캐너로 경로 수집 → 로더로 내용 읽기
  ├─ 글 → text_chunks에 모으기 → DocumentEmbedder.embed_chunks()
  └─ 그림 → 이미지/문서 이미지 인코더 → 벡터 준비
파일 정보 DB 저장 → 반환된 file_id를 경로·이미지 벡터와 연결
```

| 변수 | 진행 담당자의 메모 |
|---|---|
| documents | 이번에 저장할 파일 정보 목록 |
| pending_images | documents와 같은 순서로 모아둔 파일별 이미지 벡터 목록 |
| text_chunks | 분석 중에만 쓰는 지역 변수. 인코딩 후에는 본문 모델의 chunks가 보관 |
| file_ids | 실제 파일 경로 → DB 접수 번호 |
| image_vectors | (DB 접수 번호, 이미지 벡터) 목록 |
| failures | 읽을 내용이 없는 파일 등의 경로·이유 목록 |

`pending_images`는 아직 장부 번호를 받기 전의 대기표다.
본문 인코딩까지 끝낸 다음 `zip(documents, pending_images)`로 같은 순서의 두 목록을 짝지어 DB에 저장한다.
`zip`은 첫 번째끼리, 두 번째끼리 묶는 문법이다.
읽기 실패는 목록에 남기고 다음 파일로 넘어가며, 모델·DB 오류는 호출자에게 전달한다.

예를 들어 DB가 고양이 사진에 7번을 부여했다면 다음처럼 연결된다. 번호는 설명용 예시다.

```text
file_ids:      ".../Test1.jpg" → 7
image_vectors: (7, [이미지 특징을 나타내는 숫자들])
검색 결과:    (7, 0.22) → DB에서 7번 조회 → Test1.jpg와 실제 경로 표시
```

### search(query, mode): 맞는 창구로 보내고 결과를 돌려준다

본문이면 팀원 DocumentEmbedder의 `search()`를 호출한다.
같은 PDF의 여러 페이지가 검색되어도 파일이 반복되지 않도록 `seen`에 이미 고른 번호를 기록한다.
점수가 높은 순서에서 처음 나온 결과를 선택하므로 그 파일의 최고 점수가 남는다.

이미지면 `search()` 안에서 `query_encoder.encode_text(query)[0]`을 직접 호출해 문장을 바꾸고 임시 비교 함수에 넘긴다.
새 문장 인코더는 한 문장도 `[[숫자들]]`처럼 행이 있는 배열로 반환한다.
`encode_text(query)[0]`의 `[0]`은 첫 번째 문장의 숫자 배열을 꺼내는 뜻이다. `(1, 512)`가 비교 함수에 필요한 `(512,)`가 된다.
두 경로 모두 마지막에는 DB에서 번호에 해당하는 정보를 찾아 `(DocumentInfo, 점수)` 목록으로 반환한다.
괄호 안의 두 값을 묶은 것을 튜플이라고 부른다.

## 9. temporary_image_similarity.py — 임시 사진 비교 직원

이 코드는 사용자 요청으로 추가한 임시 구현이다. 담당자 구현을 받으면 교체할 부분이다.
로더·인코더·DB 담당자의 원본 알고리즘과 구분해 파일명과 화면에 임시 상태를 표시했다.

두 사람이 같은 방향을 가리키는 화살표를 들고 있다고 생각하면 된다.
벡터를 화살표로 보고 방향이 얼마나 비슷한지 계산하는 것이 코사인 유사도다.

```python
score = float(np.dot(query, image) / (query_length * image_length))
```

`np.dot()`은 같은 위치의 숫자를 곱해서 더하는 내적이다.
`np.linalg.norm()`으로 구한 두 벡터 길이의 곱으로 나누면 길이보다 방향을 비교하게 된다.
이 점수는 확률이 아니다. 0.24라고 해서 고양이일 확률이 24%라는 뜻이 아니다.

함수는 파일 번호별로 `best_scores` 딕셔너리를 만든다.
한 PPTX에 여러 슬라이드 이미지가 있으면 가장 높은 점수만 남긴다.
마지막에 점수 내림차순으로 정렬하고 `top_k`개를 반환한다.

현재는 기본 상위 5개이며 “고양이로 판정된 사진만” 남기는 분류 기준은 없다.
파일명이 아닌 모델 벡터로 순서를 정하므로 파일 이름에 고양이가 없어도 검색할 수 있다.
다른 프로젝트의 복사본은 경로와 DB 번호가 다르므로 각각 별도 결과가 될 수 있다.
샘플 사진 3장만 확인하려면 `assets/images` 폴더만 분석한다.

## 10. gui/window.py — 검색 결과를 보여주는 창구

`select_folder()`는 분석할 폴더를 고른다. 폴더를 바꾸면 이전 검색 상태를 지운다.
`analyze()`는 새 서비스를 만들어 분석하고 성공한 경우 검색 버튼을 활성화한다.
`search()`는 선택값을 documents 또는 images로 바꿔 서비스에 전달한다.
`show_text()`는 파일 이름·점수·경로를 텍스트 영역에 적는다.

지금 화면에는 사진 썸네일을 그리는 코드가 없다. 이미지 검색 결과도 파일 이름과 경로로 표시한다.
별도 창을 띄우는 GUI와 터미널에서 글자를 입력하는 콘솔을 app.py에서 선택한다.
분석을 별도 작업 스레드로 보내지 않으므로 모델 준비·분석 중에는 창의 응답을 기다려야 한다.

## 11. 나머지 폴더와 Python 문법 이름표

| 항목 | 비유와 의미 |
|---|---|
| assets/images | 시연 재료 보관함. 고양이 사진 Test1·Test2·Test3 |
| tests | 업무 점검표. 현재 26개 테스트가 연결·DB·읽기·비교를 확인 |
| requirements.txt | 필요한 외부 도구 목록. pip가 이 목록으로 라이브러리 설치 |
| docs | 현재 규격 설명서. 프로그램이 이 문서를 읽어 검색하지는 않음 |
| study | 개인 공부 자료. GitHub 백업에서는 제외 |
| __init__.py | 폴더를 일반 Python 패키지로 표시하는 이름표. 빈 파일도 역할이 있음 |
| .gitignore | Git에서 새 파일을 추적할 때 제외할 이름 규칙. 프로그램 실행과는 별개 |

`from database.db_info import DocumentInfo`는 해당 파일에서 이름을 가져오는 문법이다.
`self.loader`의 `self`는 지금 사용하는 서비스 객체이고, `loader`는 그 객체가 보관한 로더다.
`__init__()`는 객체를 만들 때 실행하는 초기 준비 메서드다.
`return`은 함수의 결과를 호출한 곳으로 돌려준다.
`try/except`는 오류가 발생했을 때 처리할 흐름을 적고, `raise`는 오류를 호출자에게 알린다.
`with`는 자원을 정해진 방식으로 다루는 문법이지만, 실제 종료 동작은 사용하는 객체에 따라 다르다.
예를 들어 팀원 SQLite 코드의 with는 트랜잭션 처리이며 연결 종료를 보장하지 않는다.

테스트 일부는 인코더의 출력만 대역으로 바꾼다. 테스트 26개 통과가 모든 문서의 검색 품질을 보장하는 뜻은 아니다.
실행 앱의 build_service는 실제 팀원 모델을 생성한다.

## 12. 현재 할 수 있는 일과 다음 담당자에게 넘길 일

현재 데모는 PDF·PPTX 본문 검색과 이미지 유사도 검색을 지원한다.
TXT·코드 파일·DOCX·옛 PPT·HWP/HWPX는 현재 스캐너가 수집하지 않는다.
스캔 PDF의 OCR, PDF 페이지 이미지화, 앱 재실행 후 DB·벡터 검색 복원도 없다.
이미지 비교는 임시 구현이며 DB 연결 종료 문제는 DB 담당자 점검 사항이다.

내 담당 코드를 읽을 때는 **app.py에서 조립 → service.analyze에서 전달·저장 → service.search에서 조회 → GUI에서 표시** 순서로 따라가면 된다.
팀원 인코더의 모델 내부나 DB 저장 알고리즘을 새로 만드는 것이 지금 연결 코드의 역할은 아니다.
