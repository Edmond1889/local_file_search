# 처음 보는 팀원을 위한 사진 검색 프로젝트 안내

기준: 2026-10-16의 v2 코드. Python과 Git이 익숙하지 않은 팀원도 읽을 수 있도록 작성했다.
이 문서는 공유용 설명서이며 실행 코드를 대신하지 않는다.

## 1. 이 프로젝트를 작은 사진 검색 가게라고 생각하기

손님이 사진이 들어 있는 폴더를 맡기면, 가게는 사진을 살펴보고 특징을 기록한다.
손님이 “하품하는 고양이”라고 말하면 그 문장과 어울리는 사진을 찾아 보여준다.

| 프로젝트 구성 | 가게에 비유하면 | 실제 역할 |
|---|---|---|
| gui.py | 손님이 이용하는 접수 창구 | 폴더 선택·분석 버튼·검색창·미리보기 |
| imaging/ | 맡긴 사진을 꺼내 확인하는 직원 | 사진 파일 찾기·손상 검사·이미지 읽기 |
| encoders/ | 사진과 문장을 공통 특징표로 바꾸는 직원 | 이미지·문장의 임베딩 생성 |
| storage/ | 사진 정보 장부와 특징 검색 장치의 설계 | SQLite와 FAISS를 다루는 코드 |
| adapters/ | 직원마다 다른 서식을 맞추는 담당자 | 필드 이름·함수 이름·배열 형식 변환 |
| services/ | 일을 순서대로 배정하는 진행 담당자 | 분석·검색 호출 순서 관리 |
| real_services.py | 실제 근무자를 정해 조를 편성하는 곳 | 실제 도구 생성·공유·수명 관리 |
| interface.py | 직원이 제공해야 할 업무의 규격표 | 함수 이름·입력·출력 규격 |
| models/ | 직원들이 주고받는 공통 서식 | 파일 정보·분석 보고서·검색 결과 |
| tests/ | 가게가 제대로 일하는지 확인하는 점검표 | 자동 검증 코드 |
| assets/ | 연습할 때 쓰는 준비물 | 현재는 샘플 사진 3장 |
| artifacts/ | 따로 보관해둔 옛 점검 기록 | 현재는 수동 검증 JSON, GUI 출력 아님 |
| reports/ | 일이 끝나면 자동 발급하는 분석 영수증 | GUI 분석 완료 후 생성한 JSON, Git 제외 |
| demo/ | 실제 도구 없이 동선을 연습하는 모의 직원 | 가상 데이터 구현 |
| docs/ | 업무 설명서와 과거 회의록 | 구조·규격·출처·검증 기록 설명 |
| requirements/ | 필요한 외부 도구의 준비 목록 | pip 설치용 라이브러리 목록 |

비유 속 특징표는 사람이 읽는 문장형 설명이 아니다. 실제로는 모델이 계산한 숫자 배열이다.

## 2. assets와 artifacts는 왜 따로 두었나?

### assets/ — 사용하기 전에 준비한 재료

현재 [assets/images/](../assets/images/)에는 Test1.jpg, Test2.jpg, Test3.jpg가 있다.
실제 분석과 검색을 확인할 때 사용할 수 있는 고양이 샘플 사진이다.

사진 검색 가게라면 직원 교육용으로 미리 준비한 사진 봉투라고 생각하면 된다.
프로그램이 분석해서 만들어낸 파일이 아니라, 입력으로 사용할 자료다.

GUI에서 반드시 이 폴더만 선택해야 하는 것은 아니다. 사용자가 다른 사진 폴더를 선택해도 된다.
이 샘플 폴더가 없더라도 프로그램 코드 전체가 사라지는 것은 아니지만, 문서에서 안내하는 샘플 시연은 할 수 없게 된다.

### artifacts/ — 별도 검증 후 수동으로 보관한 과거 기록

현재 파일은 [CAT_SEARCH_CHECK_2026-10-14.json](../artifacts/checks/CAT_SEARCH_CHECK_2026-10-14.json)이다.
개발 중 별도로 모델 검증을 실행한 뒤 샘플 사진과 “하품하는 고양이” 등의 검색 결과를 저장한 수동 기록이다. GUI가 자동 생성한 파일이 아니다.

가게의 재료가 사진이라면, 이 파일은 “그 사진으로 점검해봤더니 이런 결과가 나왔다”는 점검 기록이다.
JSON은 프로그램과 사람이 구조를 읽을 수 있게 데이터를 기록하는 텍스트 형식이다.

이 JSON을 읽어서 현재 검색 결과를 만드는 것은 아니다. 실제 검색은 모델·FAISS·DB를 사용한다.
또 GUI를 실행할 때마다 이 파일이 자동 갱신되도록 연결해둔 것도 아니다. 저장해둔 과거 검증 기록이다.

```text
assets/images/의 사진 → GUI 분석 완료 → reports/의 자동 분석 보고서
입력으로 쓰는 자료                     실행할 때 생성되는 기록

artifacts/checks/의 기존 JSON은 별도로 저장해둔 과거 수동 검증 기록
```

assets와 artifacts는 관례적인 폴더 이름이다. Python이 이 이름을 보고 특별한 동작을 하는 것은 아니다.

## 3. demo/ — 실제 검색 없이 연결을 연습하기

[demo/demo_adapters.py](../demo/demo_adapters.py)에는 DemoScanner, DemoImageLoader,
DemoImageEncoder, DemoTextEncoder, DemoRepository, DemoVectorIndex가 있다.

실제 사진·AI 모델·영구 DB를 준비하기 전에 “직원들이 정해진 순서로 일을 주고받는가?”를 확인하기 위한 가상 도구다.
예를 들어 고정된 사진 이름 세 개를 돌려주고, 그중 하나를 손상 사진처럼 처리한다.
문장 인코더는 모든 검색 문장에 같은 벡터를 반환하므로 실제 검색 품질을 평가할 수 없다.

| 명령 | 동작 |
|---|---|
| python gui.py | 실제 사진·모델·SQLite·FAISS를 연결한 GUI |
| python gui.py --demo | 가상 데이터를 사용하는 GUI |
| python app.py | 가상 데이터를 사용하는 콘솔 데모 |

콘솔은 터미널에서 글자로 입력·결과를 주고받는 방식이고, GUI는 버튼과 검색창이 있는 별도 창이다.
현재 웹 화면은 없다. 새로 뜨는 창은 Tkinter 데스크톱 GUI다.

demo는 옛 코드라는 이유만으로 지우면 안 된다. 현재 --demo 기능과 서비스 테스트도 이 파일을 사용한다.
다만 실제 사진 검색에서 기본으로 사용하는 도구는 real_services.py가 조립한 실제 구현이다.

## 4. docs/ — 팀원이 함께 읽는 설명서

docs는 documents의 줄임말로 쓰는 폴더 이름이다. 지금은 기능 설명과 협업 기록을 모아두었다.

| 문서 | 궁금할 때 읽기 |
|---|---|
| [README.md](README.md) | 공유 문서 전체 목록 |
| [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) | 파일이 어디 있고 무엇을 수정해야 하는가? |
| [CODE_OWNERSHIP.md](CODE_OWNERSHIP.md) | 누가 어떤 기능을 작성했고 원래 위치는 어디였는가? |
| [INTERFACE_GUIDE.md](INTERFACE_GUIDE.md) | 어떤 함수가 어디서 호출되는가? |
| [DB_ADAPTER_GUIDE.md](DB_ADAPTER_GUIDE.md) | 공통 파일 정보와 DB 필드가 어떻게 대응하는가? |
| [DEMO_CODE_INVENTORY.md](DEMO_CODE_INVENTORY.md) | 옛 사본과 현재도 사용하는 데모를 어떻게 구분하는가? |

프로그램은 현재 docs 안의 설명서를 읽어 사진을 검색하지 않는다.
다만 개발자가 파일을 옮길 때 설명서의 링크와 명령도 함께 바꿔야 팀원이 잘못된 경로를 따라가지 않는다.
history 문서는 당시 기록이므로 본문에 예전 경로가 나올 수 있다. 현재 경로는 구조 안내를 기준으로 한다.

## 5. interface.py — 설명서처럼 보이지만 실행 코드에서 참조하는 규격

[interface.py](../interface.py)는 “사진 로더라면 이런 함수를 제공하자”라는 약속을 Python으로 적은 파일이다.

```python
class ImageLoader(Protocol):
    def load(self, file_path: str) -> Any: ...
```

이것은 사진을 여는 구현이 아니다. “load는 사진 경로를 받고 이미지 데이터를 돌려준다”는 함수의 모양이다.
실제 사진을 여는 내용은 imaging/image_loader.py의 DefaultImageLoader.load()에 있다.

가게의 규격표에는 “사진 읽기 담당자는 사진을 읽어 다음 직원에게 전달한다”고 적고,
실제 직원은 그 업무를 수행하는 것으로 생각하면 된다.

- Protocol: 어떤 함수를 제공해야 하는지 표현하는 도구.
- str: 문자열을 뜻하는 타입 표시.
- Any: 이 규격에서는 반환 자료형을 구체적으로 제한하지 않았다는 뜻.
- ...: 이 자리에서는 함수의 실제 처리 내용을 작성하지 않았다는 표시.

Protocol이 알맞은 팀원 함수를 자동으로 찾아 연결하지는 않는다. 실제 객체는 서비스 생성 시 전달한다.
타입 표시만으로 실행 중 입력·출력을 자동 검사하지도 않는다.
같은 파일의 ImageLoadError는 로더가 발생시키고 서비스가 받아 처리하는 실제 오류 종류다.
따라서 이 파일을 일반 메모처럼 옮기거나 삭제하면 현재 import가 깨진다.

## 6. models/ — AI 모델이 아니라 공통 전달 서식

이 폴더의 model은 데이터 구조라는 뜻이다. AI 가중치가 들어 있는 폴더가 아니다.

| 자료형 | 서식에 비유하면 | 담는 정보 |
|---|---|---|
| FileInfo | 사진 접수 카드 | 이름·경로·확장자·크기·수정 시각 등 |
| AnalysisFailure | 읽기 실패 메모 | 어떤 파일을 왜 읽지 못했는가? |
| AnalysisReport | 분석 완료 보고서 | 저장 성공한 파일과 읽기 실패 목록 |
| SearchResult | 검색 결과 카드 | FileInfo와 이번 검색의 점수 |

예를 들어 result.file.name으로 사진 이름을, result.score로 검색 점수를 읽는다.
사진 이름은 파일 정보이고, 검색 점수는 검색어에 따라 달라지므로 따로 묶는다.

@dataclass는 이런 서식을 적은 필드를 바탕으로 생성자 등을 만들어주는 Python 기능이다.
FileInfo는 파일 정보만 담는다. 실제 사진 픽셀과 임베딩 벡터를 모두 이 객체에 넣는 구조는 아니다.

## 7. real_services.py — 실제 도구를 조립하는 곳

어댑터가 서로 다른 서식을 맞춘다면, [real_services.py](../real_services.py)는 그 도구들을 만들어 한 조로 묶는다.

1. 이미지·문장 인코더를 준비한다. 첫 분석 때 모델을 로드하고 재분석 때 재사용한다.
2. 스캐너와 이미지 로더를 준비한다.
3. 임시 SQLite DB와 FAISS 인덱스를 만든다.
4. 필요한 어댑터로 감싼다.
5. AnalysisService와 SearchService에 같은 저장소·인덱스를 전달한다.

분석 직원이 기록한 장부를 검색 직원도 봐야 하므로 두 서비스가 같은 객체를 공유해야 한다.
서로 다른 인덱스를 주면 분석에 성공해도 검색 쪽에서는 그 사진 벡터를 못 찾을 수 있다.

현재 저장 정책도 여기서 정한다. 분석마다 새 임시 DB와 메모리 인덱스를 쓰므로 재실행하면 재분석해야 한다.
storage/에는 저장을 다루는 코드가 있고, 현재 실행 중 생성되는 DB 파일은 OS 임시 폴더에 있다.
assets나 artifacts가 현재 DB 보관 폴더인 것은 아니다.

## 8. __init__.py — 폴더에 붙이는 패키지 이름표

```text
storage/
├── __init__.py
└── db_manager.py
```

빈 __init__.py는 storage를 일반적인 Python 패키지로 명시한다.
패키지는 관련 Python 모듈을 묶은 단위이고, 모듈은 여기서는 db_manager.py 같은 Python 파일로 생각하면 된다.

```python
from storage.db_manager import Repository
```

위 코드는 storage 폴더의 db_manager 모듈에서 Repository를 가져온다는 뜻이다.
이번 정리에서는 새로 나눈 imaging, encoders, storage, demo 폴더를 명확한 패키지로 표시하려고 빈 파일을 추가했다.
빈 초기화 파일 자체가 DB를 만들거나 사진을 처리하는 것은 아니다.
초기화 파일에 코드를 쓰면 패키지를 처음 import할 때 실행될 수 있지만 현재 이 네 파일은 비어 있다.

현대 Python에는 __init__.py 없이도 패키지로 사용하는 방식이 있다.
현재 models와 services도 그렇게 import되므로 모든 폴더에 무조건 추가해야 하는 파일은 아니다.
assets·artifacts·reports·docs는 Python 코드 패키지로 만든 폴더가 아니므로 이 이름표를 붙이지 않았다.

| 비슷한 이름 | 의미 |
|---|---|
| __init__.py | 패키지 폴더의 초기화 파일 |
| def __init__(self, ...) | 클래스의 객체를 만들 때 초기 상태를 정하는 메서드 |

## 9. tests/ — 실행 가능한 자동 점검표

가게 점검표에 “손상 사진 하나가 있어도 다음 사진을 처리하는가?”라고 적을 수 있다.
tests는 그런 확인을 사람이 매번 클릭하는 대신 Python 코드로 실행하도록 만든 것이다.

| 파일 | 점검 대상 |
|---|---|
| test_services.py | 호출 순서·같은 파일 ID 사용·손상 사진·빈 검색어 처리 |
| test_repository_adapter.py | 실제 SQLite·FAISS 연결과 메타데이터 변환·보존 |
| test_real_services.py | 실제 도구 조립·재분석·벡터 입력 검사 |
| test_gui_events.py | 분석 성공·실패 후 검색 버튼 상태 등 GUI 이벤트 처리 |

```powershell
python -m unittest discover -s tests -v
```

이 명령으로 실행한다. 평소 python gui.py로 앱을 켠다고 테스트가 자동으로 함께 실행되는 것은 아니다.
현재 36개 테스트가 통과했다는 것은 정해둔 조건의 검증을 통과했다는 의미다.
일부 테스트는 AI 모델 대신 정해진 벡터를 사용하므로 실제 검색 품질까지 증명하지는 않는다.
테스트는 사진 검색의 필수 실행 부품은 아니지만 변경 후 연결을 확인하기 위해 보관한다.

## 10. requirements/ — 외부 라이브러리 준비 목록

세 TXT는 설명 메모가 아니라 pip가 읽는 설치 목록이다.

```text
requirements/requirements-app.txt    앱 실행에 필요한 목록
  └─ requirements-db.txt            DB·FAISS 목록 포함
       └─ requirements.txt          기본 모델 목록 포함
```

실제 GUI를 준비할 때는 저장소 루트에서 다음 명령을 사용한다.

```powershell
python -m pip install -r requirements/requirements-app.txt
python gui.py
```

세 파일을 따로 설치할 필요는 없다. app 목록이 나머지를 포함한다.
설치는 GUI를 실행할 Python 환경에서 해야 한다.
파일 내용과 내부 -r 행은 유지한 채 세 파일을 같은 폴더로 옮겼다.
자세한 역할과 작성 이력은 [설치 목록 안내](../requirements/README.md)에 있다.

## 11. 처음부터 끝까지 한 번 따라가기

```text
분석
GUI에서 사진 폴더 선택
  → 스캐너가 FileInfo 목록 생성
  → 로더가 사진을 PIL 이미지로 읽음
  → 이미지 인코더가 특징 벡터 생성
  → 어댑터가 DB에 맞는 파일 정보로 변환
  → SQLite에 파일 정보 저장, 파일 ID 반환
  → 같은 ID로 FAISS에 벡터 저장
  → AnalysisReport를 JSON으로 reports/에 자동 저장
  → GUI에 분석 결과와 보고서 경로 표시 (저장 실패 시 오류 안내)

검색
GUI에 “하품하는 고양이” 입력
  → 문장 인코더가 검색 벡터 생성
  → FAISS가 유사한 벡터의 파일 ID와 점수 반환
  → SQLite에서 그 ID의 파일 정보 조회
  → SearchResult로 묶어 GUI에 전달
  → 선택한 결과의 파일 경로로 사진 미리보기
```

사진 경로, 이미지 픽셀, 임베딩 벡터, 파일 ID는 각각 다른 값이다.
예를 들어 C:/photos/cat.jpg는 주소, PIL 이미지는 읽은 사진 데이터,
512개 숫자는 모델이 계산한 특징, 7번은 DB와 FAISS에서 같은 사진을 찾기 위한 식별자다.
유사도 0.26을 정확도 26%로 읽지는 않는다. 현재 점수는 확률이 아니다.

## 12. 어떤 파일을 보관하거나 이동해도 될까?

| 종류 | 현재 예 | 판단 |
|---|---|---|
| 실행·연결 코드 | interface, models, services, real_services, gui | 프로그램이 사용하므로 경로와 참조를 함께 관리 |
| 가상 데모 코드 | app.py, demo/ | --demo·콘솔·테스트에서 아직 사용 |
| 점검 코드 | tests/ | 실행과 별개지만 변경 검증을 위해 유지 |
| 입력 샘플 | assets/ | 예제 입력이며 사용자 사진 폴더를 대신할 수 있음 |
| 과거 수동 기록 | artifacts/ | 별도 검증 결과 보존용, GUI 출력 아님 |
| 자동 분석 보고서 | reports/ | GUI 분석 후 생성, 검색 복원용 데이터는 아님 |
| 설명 문서 | docs/ | 개발·협업 안내용, 링크 유지 필요 |
| 설치 목록 | requirements/ | 설치 명령과 포함 관계를 유지해야 함 |
| 자동 생성 캐시 | __pycache__, .pyc | 소스가 아니며 실행 시 재생성됨 |

옛 project 사본과 현재 v2 파일은 구분한다. 같은 이름이어도 현재 실행에 재사용된 코드가 있다.
구파일 목록은 [데모 코드·보관 후보](DEMO_CODE_INVENTORY.md)를 확인한다.

폴더를 이동하는 것도 import, 설치 명령, 문서 링크, 다른 팀원의 병합에 영향을 준다.
따라서 기능 내용은 유지하고 이전 위치와 새 위치를 남긴 뒤 테스트와 PR로 확인한다.
현재 원본 main에도 interface, models, tests, real_services가 이미 있다. 이전 통합 PR로 들어간 파일들이다.
이번 정리에서 이 구조를 처음부터 새로 만든 것으로 해석하지 않는다.

## 13. 어디부터 읽으면 좋을까?

먼저 이 문서의 폴더 표와 전체 흐름을 보고, [담당자·출처](CODE_OWNERSHIP.md)로 각 기능의 주체를 확인한다.
그다음 models/file_info.py → interface.py → services/analysis_service.py → real_services.py 순서로 읽으면
“무슨 정보를 주고받으며 실제 객체는 어디서 연결하는가?”를 따라갈 수 있다.
구체적인 함수 위치는 [연결 규격 안내](INTERFACE_GUIDE.md)를 참고한다.


## 14. 새 자동 보고서는 가게에서 발급하는 분석 영수증

직원이 일을 마친 뒤 “몇 장을 처리했고 어떤 사진을 읽지 못했는가”를 영수증으로 남기는 것과 같다.
GUI에서 분석이 완료되면 reports/에 시각·성공·실패·소요 시간 등을 담은 JSON 한 개를 자동 저장한다.
보고서 칸에서 저장 위치를 복사할 수 있다. 같은 분석으로 검색해도 보고서가 검색 결과로 바뀌지는 않는다.
현재 검색 문장·검색 결과의 자동 기록은 하지 않는다.

보고서 쓰기만 실패하면 안내를 표시하고 완료된 분석 결과와 검색은 유지한다.
분석 자체가 중단되면 완료 영수증을 만들지 않는다. --demo 보고서에는 가상 데이터임을 표시한다.
사진을 분석한 기록이지 DB와 벡터의 영구 보관이 아니므로 앱 재실행 시에는 재분석해야 한다.
샘플 JSON을 미리 reports에 넣어두지 않는다. 폴더는 실제 저장 시 생기고 Git에서는 제외한다.
자세한 항목은 [분석 보고서 안내](REPORTS_GUIDE.md)를 참고한다.
